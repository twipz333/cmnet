# Dota 2 Draft Advisor — Техническое задание

> Этот файл — контекст проекта для Claude Code. Здесь зафиксированы цель, архитектура
> и принятые решения. Перед написанием кода прочитай его целиком и следуй ему.

## 1. Цель

Локальный инструмент-советник по фазе пиков/банов в Dota 2. На вход — текущее состояние
драфта (пики, баны обеих команд, чья очередь и пик это или бан). На выход:

1. **Предикт намерений врага** — распределение вероятностей `P(герой | состояние драфта)`:
   что вражеская команда вероятнее всего пикнет/забанит следующим.
2. **Рекомендация** — лучшие пики/баны для своей команды на текущем шаге, с оценкой.

Дополнительно (опциональный слой): подкрутка рекомендаций под **конкретных вражеских
игроков** на основе их истории матчей.

Ключевое требование к продукту: **детерминированность между устройствами**. Один человек
обучает модель, раздаёт бандл друзьям; на стадии драфта при одинаковом входе все видят
**идентичный** результат (вплоть до порядка в ранжировании).

Проект **некоммерческий**, для личного/дружеского использования.

## 2. Не-цели и границы

- Не монетизируем. Уважаем ToS источников (STRATZ требует атрибуцию; OpenDota — free tier).
- **Не скрейпим Dotabuff** (нет публичного API, за Cloudflare, хрупко, против ToS).
- **Не скрейпим Dota2ProTracker** — у него нет публичного API, он сам работает поверх STRATZ.
  Идём напрямую к STRATZ.
- Не строим обучение с подкреплением / self-play. Рекомендация — это поиск поверх
  обученной оценочной модели, а не RL.
- Реалистичные ожидания по точности (см. §10): это советник, а не оракул.

## 3. Технологический стек и жёсткие ограничения

- **Язык: Go.** Весь runtime-приклад должен собираться в **один статический бинарь под
  Windows** (`GOOS=windows GOARCH=amd64 CGO_ENABLED=0 go build`). Никаких DLL и внешних
  рантаймов.
- Хранилище кэша матчей: **pure-Go SQLite** (`modernc.org/sqlite`) — чтобы не тянуть CGO
  и не ломать статическую сборку. Допустима альтернатива: bbolt / parquet, если так проще.
- **Обучение тоже на Go.** Модель намеренно простая (см. §5), поэтому отдельный
  Python-пайплайн не нужен — это упрощает детерминизм и оставляет один toolchain.
  - *Запасной путь на будущее, если упрёмся в потолок простой модели:* обучать в Python
    (PyTorch), экспортировать веса в портируемый формат, инференс на Go читает веса и делает
    forward pass вручную. Сейчас НЕ делаем — закладываем только pure-Go.
- UI: полированный **TUI** на стеке Charm (bubbletea + lipgloss + bubbles) — чистый Go,
  не ломает статическую сборку. Подробнее — §8.
- Один бинарь с подкомандами (cobra/стандартный flag), например:
  - `advisor sync` — инкрементальная подкачка данных в локальный кэш.
  - `advisor train` — обучение из кэша, выдаёт **бандл** (см. §6).
  - `advisor serve` — режим советника: GSI-сервер + рекомендатор + **TUI** (это то, что запускают друзья).
  - `advisor scout` — (опц.) фетч и заморозка снапшота оппонентов.

## 4. Источники данных и ingestion

### Источники
- **STRATZ** (GraphQL, `api.stratz.com/graphql`): фильтрация матчей по рангу/лиге, получение
  ID матчей, перформанс игроков по героям. Один запрос отдаёт данные до ~100 матчей.
  Нужен токен (логин на stratz.com). Атрибуция обязательна.
- **OpenDota** (REST): детальные данные матча с `pick_ban`, эндпоинты по игрокам
  (`/players/{id}/recentMatches`, `/players/{id}/heroes`), список героев (`/heroes`).
- Рабочий паттерн: ID матчей и фильтр по рангу — из STRATZ; детальные pick/ban — добираем
  из OpenDota.

### Лимиты (закладывать в лимитер)
- OpenDota: 50 000 вызовов/месяц, 60 req/min.
- STRATZ (залогиненный токен): 20 req/s, 250/min, 2000/hour, 10 000/day.

### Стратегия (лимиты не должны быть проблемой)
- **Инкрементальный sync**: тянем только матчи новее последнего синхрона. Первый полный
  пулл дорогой, дальше — дешёвая дельта.
- Агрессивный **локальный кэш** (SQLite): один раз скачали — больше не дёргаем.
- **Token-bucket лимитер** на каждый источник + экспоненциальный backoff на HTTP 429.
- Данные тегируются **патчем**. Используем **скользящее окно** (последний ~месяц) c
  **весами по свежести** (свежие матчи весомее). Фокус на высокий ранг (например, immortal /
  high MMR) и/или про-матчи — там сигнал чище.
- **Переобучение** — фоновый процесс: под крупный балансовый патч или добавление героя
  делаем полный ретрейн (с ресайзом выходного слоя под новый список героев). См. §6 про
  hero map в бандле — герои меняются (сейчас ~127), индексы нельзя хардкодить.

## 5. Модель

Две головы (можно две отдельные простые модели):

### 5.1 Предиктор следующего пика/бана
- Архитектура «bag-of-heroes» (в духе draftnet): вход — multi-hot векторы (пики и баны
  каждой команды) + флаг «сейчас пик или бан». Выход — softmax-распределение по героям.
- Реализация: логистическая регрессия / неглубокий MLP. Тренируется и инферится на Go.

### 5.2 Оценка силы драфта (win-prob)
- `P(radiant win | составы обеих команд)`. Вход: присутствие героев + (по возможности)
  предрассчитанные матрицы **synergy/counter** из винрейтов (их можно считать прямым счётом
  из кэша, без ML — это часто не хуже сетки).
- Модель: логрег / неглубокий MLP. Обязательно **калибровка** вероятностей (хотя бы
  изотоническая/Platt), чтобы «65%» значило ~65%.

### 5.3 Рекомендатор
- Не отдельная сеть, а **поиск по дереву драфта** поверх win-prob модели: для каждого
  кандидата на текущий шаг оцениваем итоговую силу, перебирая разумные продолжения
  (minimax/expectimax или beam search).
- Branching factor ~127 → обязательно **отсечение**: рассматриваем только top-N мета-героев
  + (если включён слой оппонентов) комфорт-героев врага.
- **Поиск обязан быть детерминированным** (см. §6): фиксированный порядок обхода кандидатов,
  стабильная сортировка, никаких итераций по `map` для order-sensitive логики (в Go порядок
  обхода map рандомизирован).

> Почему простая модель: эмпирически на этой задаче логрег ≈ нейросети, потолок предсказания
> победы по драфту ~0.60–0.65 ROC AUC. Простая модель даёт почти ту же точность, тривиально
> детерминируется и собирается в чистый Go.

## 6. Детерминизм и формат бандла

Это самая важная часть требований. Источник недетерминизма — даже не обучение (его делает
один человек), а **инференс**: микроразличия во float между платформами (x86/arm, порядок
редукций, FMA-контракция `a*b+c`) могут флипнуть порядок двух близких по оценке героев — и
у друга «лучший пик №1» окажется другим.

### Решения
1. **Самодостаточный версионированный бандл** — единственный артефакт, который раздаётся.
   Друзья НЕ переобучают, только инферят на бандле. Бандл содержит:
   - веса обеих моделей;
   - **hero index map** (id → индекс) — внутри бандла, не из локальных констант;
   - тег патча, версию схемы фич, версию кода;
   - `sha256`-хэш содержимого как `bundle_version`.
   Формат: один файл (gob или JSON; допустимо завернуть в zip). При загрузке `serve`
   **проверяет версию** и **отказывается работать** на несовпадающем бандле — чтобы не было
   тихого расхождения.
2. **Детерминированный инференс**:
   - инференс модели — однопоточный (модель крошечная, гонок нет);
   - **округление скоров** до фиксированной точности (напр. 5 знаков) ПЕРЕД ранжированием;
   - **стабильный tie-break по hero_id** при сортировке.
   Это нейтрализует любые sub-ULP различия (включая FMA) между платформами.
3. Никаких `map`-итераций там, где важен порядок; везде `sort.SliceStable` с явным
   вторичным ключом.

## 7. Живой ввод драфта

- **Основной путь — GSI (Game State Integration)**: бинарь поднимает локальный HTTP-сервер,
  Dota POST-ит туда JSON состояния игры. Парсим блок драфта (CM: пики/баны команд, чей ход).
  Для работы нужен конфиг-файл GSI, который кладётся в папку
  `.../dota 2 beta/game/dota/cfg/gamestate_integration/` и указывает на локальный endpoint —
  бинарь должен уметь сгенерировать/положить этот конфиг по команде (`advisor gsi-install`).
- **Фолбэк — ручной ввод**: тот же TUI (см. §8), выбор героев через список с фильтрацией.
- Для требования «у всех одинаково»: вход у всех должен быть одинаков. В одном лобби каждый
  поднимает GSI локально → состояние драфта идентично у всех автоматически.

## 8. Пользовательский интерфейс (TUI)

Целевой UX — **как у jiratui** (он на Python/Textual+Rich): полированный, компонентный TUI
со скринами/панелями, клавиатурной навигацией, темами и встроенным help. **НЕ** голая
консоль и **НЕ** GUI (Qt и подобное). User-friendly, но целиком в терминале.

### Стек (чистый Go, сохраняет статический .exe и `CGO_ENABLED=0`)
- **`charmbracelet/bubbletea`** — ядро, архитектура The Elm Architecture (Model / Update / View).
  Это Go-аналог Textual.
- **`charmbracelet/lipgloss`** — стилизация и layout (рамки, цвета, колонки, выравнивание) —
  аналог Rich.
- **`charmbracelet/bubbles`** — готовые компоненты: `list`, `table`, `textinput`, `viewport`,
  `spinner`, `help` (показ кейбиндов), `key` (маппинг клавиш).
- *Опционально:* `charmbracelet/glamour` (рендер markdown, если понадобится), `charmbracelet/log`.

### Примерная раскладка под эту задачу
- **Доска драфта**: пики/баны обеих команд, текущая фаза и чей ход.
- **Рекомендации**: ранжированный список «лучший пик/бан сейчас» со скором и кратким «почему».
- **Предикт врага**: топ вероятных следующих пиков/банов противника.
- **Комфорт-герои врагов** (если включён слой скаута, §9).
- **Статус-бар**: свежесть данных, версия бандла, статус GSI-подключения, индикатор
  «снапшот оппонентов заморожен/нет».
- **Help-оверлей** с кейбиндами (как `?` в jiratui) и темами.

### Архитектурное правило
- TUI — это **слой View поверх детерминированного ядра**. TEA-разделение Model/Update/View
  ложится идеально: GSI-события и ввод пользователя → `Update` меняет state → рекомендатор
  (детерминированное ядро из core-пакетов) пересчитывает → `View` рендерит.
- **Вся логика рекомендаций/предикта живёт в core-пакетах. TUI ничего не вычисляет сам** —
  только рендерит то, что отдало ядро. Это критично для требования «у всех одинаково» (§6):
  UI не должен быть источником недетерминизма.

## 9. Данные по оппонентам — три слоя (graceful degradation)

Анализ строится из трёх слоёв с нарастающей конкретикой. Каждый следующий слабее по объёму,
но точнее и ближе к конкретному сопернику. **Слой 1 — это база (prior), слои 2 и 3 —
поправки поверх (evidence).** Они описывают разное, поэтому складываются не одинаково (см.
«Блендинг»).

| Слой | Что отвечает | Источник / окно | Где живёт | Сэмпл |
|---|---|---|---|---|
| **1. Мета** | что вообще сильно/популярно в текущей мете на нашем уровне | обучающий кэш, окно **T-31д**, фильтр по среднему MMR матча вокруг нашего Battle Cup-тира | **бандл** (`train`) | большой |
| **2. Игроки** | что эти конкретные люди умеют/любят (пул, комфортки) | OpenDota/STRATZ по `account_id`, окно ~месяц | **снапшот** (`scout`) | средний |
| **3. Команда сегодня** | что эта команда уже показала в этом Battle Cup: фёрст-пик, что банят, в какой последовательности | драфты матчей соперника **в текущем ивенте** (окно «сегодня/событие») | **снапшот** (`scout`) | крошечный (1–3 драфта) |

Ключевое: трёхслойка ложится на уже существующее разделение **бандл (статика) vs снапшот
(живые данные)**. Слой 1 — в бандле, слои 2–3 — в замороженном снапшоте. Детерминизм цел.

### Где это применяется
- Слой 1 питает **обе** головы модели (§5): предиктор `P(герой|state)` и win-prob.
- Слои 2 и 3 уточняют **только голову «предикт врага»** (что соперник пикнет/забанит). Мои
  собственные пик-рекомендации по-прежнему опираются на win-prob слоя 1 — просто потребляют
  более точный предикт врага.

### Слой 3 — почему он не «улучшенный слой 2»
Слой 2 — про индивидуальные скиллы пятерых. Слой 3 — про **командную** драфт-стратегию
(роли, кто на какой позиции, какие связки собирают, что приоритетно банят). Те же пятеро в
Battle Cup могут играть не теми героями, что в соло-пабах за месяц. Поэтому слой 3 иногда
**противоречит** слою 2 — и это ценно (игрок месяц спамит мид-Инвокера, а сегодня дважды
встал на саппорта → он не их мидер).

### Блендинг (взвешенная комбинация в лог-пространстве)
Не наивное перемножение. Голова «предикт врага»:
```
score(герой) = log P1(герой | состояние)     # слой 1, база
             + w2     · log aff2(герой)       # слой 2
             + w3_eff · log aff3(герой)       # слой 3
→ softmax → вероятность
```
- `w3 > w2`: слой 3 доминирует, но **не стирает** слои 1–2 (мягкий блендинг, не override).
- **Вес слоя 3 масштабируется по объёму наблюдений в ивенте**: `w3_eff = w3_max · n/(n+k)`,
  где `n` — число драфтов соперника, уже сыгранных сегодня (раунд 1 → n=1, мягко; полуфинал
  → n=2–3, крепче). `k` — сглаживающая константа. Так слой 3 не переобучается на 1–3 матчах
  и усиливается по ходу сетки сам.
- `aff2`/`aff3` **аддитивно сглаживаются**, чтобы `log(0)` не обнулял невиданных героев.
- Все веса (`w2`, `w3_max`, `k`) — в конфиг.

### Окна — разные у каждого слоя
Слой 1 — T-31д. Слой 2 — ~месяц. Слой 3 — «текущее событие/сегодня». Это **три разных
запроса с разными окнами**, в коде не смешивать.

### Точка входа и доступ к данным
- **pick/ban — это данные уровня матча, а не игрока.** Поэтому для слоя 3 достаточно
  резолвнуть **хотя бы один** ник врага → `account_id`: через его историю находим матч
  команды, а в записи матча лежит полный драфт обеих команд (даже у анонимных тиммейтов
  виден герой и сторона — скрыт лишь их `account_id`). Один открытый враг раскрывает драфты
  всей команды.
- Слой 3 использует **ту же точку входа**, что и слой 2 (один резолвнутый `account_id`), —
  он не «дороже» по доступу, просто тянет из найденного матча весь драфт, а не affinity.
- Ограничения (закладывать, не бороться): «Expose Public Match Data» по умолчанию выключена;
  ники врагов резолвятся через поиск STRATZ ненадёжно — но нужен ровно **один** хит из пяти.

### Цепочка деградации (каждый слой отваливается независимо)
- Нет слоя 3 (первая стадия Battle Cup, или матч команды не найден) → работаем на **1 + 2**.
- Нет точки входа (ни один `account_id` не резолвится) → работаем на **слое 1** (чистая мета).

### Тайминг (Battle Cup)
Скаутим **между раундами**: выиграл четвертьфинал → узнал соперника по полуфиналу → пара
минут до матча → `scout` тянет слои 2–3, замораживает снапшот, раздаёт тиммейтам → заходим в
драфт уже с ним.

### Детерминизм при живых данных
- **Один человек** тянет снапшот (фикс. окна по слоям + фикс. timestamp заморозки),
  **замораживает** в файл и **раздаёт** остальным. Все блендят на **одном** снапшоте.
- Снапшот версионируется и логически отделён от бандла (бандл = статика; снапшот = слои 2–3
  для конкретного матча). Блендинг — чистая детерминированная функция от (бандл, снапшот, state).
- *Опционально (прозрачность, не отдельный скоринг):* в UI можно тегировать предсказание
  меткой происхождения (напр. «seen this event»), когда его вытянул слой 3 — чтобы человек
  понимал, почему. Скоринг при этом единый, без отдельной панели.

## 10. Ожидания по точности (зафиксировать в README, не обещать лишнего)

- Win-prob по чистому драфту: потолок ~0.60–0.65 ROC AUC.
- Ценность инструмента: мета-осознанные подсказки пик/бан + предугадывание комфорт-пиков
  врага, а **не** точное предсказание исхода.
- На свежем патче с малым объёмом данных точность ниже — это ожидаемо.

## 11. Предлагаемая этапность

- **MVP**: `sync` (STRATZ→OpenDota, кэш, лимитер) → `train` (win-prob + предиктор, бандл с
  версией) → `serve` с **TUI** (§8) на ручном вводе + детерминированный рекомендатор
  (округление + tie-break). Проверить: один бандл на двух машинах → идентичный топ рекомендаций.
- **M2**: GSI как источник состояния драфта вместо ручного ввода (+ `gsi-install`); TUI
  обновляется от GSI-событий.
- **M3**: synergy/counter матрицы и beam-search рекомендатор с отсечением.
- **M4**: данные по оппонентам — слои 2 и 3 (§9): `scout` тянет снапшот (affinity игроков +
  драфты команды в текущем ивенте), лог-линейный блендинг с масштабированием веса слоя 3 по
  числу драфтов, цепочка деградации; панель в TUI (за флагом). Слой 1 уже в бандле с MVP.
- **M5**: качество данных (recency weighting, фильтр по рангу/патчу), калибровка, retrain-флоу;
  полировка TUI (темы, help-оверлей).

## 12. Открытые вопросы / риски

- Насколько надёжно GSI отдаёт `account_id` врагов во время драфта (для §9) — проверить
  экспериментально; вероятно, ненадёжно в пабах.
- Объём про/high-MMR CM-драфтов на свежем патче может быть мал → возможно, расширять окно
  или ранговый фильтр.
- FMA/float-различия между платформами — снимаются округлением+tie-break (§6), но проверить
  тестом «один бандл, один вход, две ОС/арки → байт-в-байт одинаковый вывод».
